# GPUI capability research for a frameless / transparent / always-on-top / click-through desktop overlay (Echosight → GPUI rewrite evaluation)

Date: 2026-11-09. All GPUI source citations are against `zed-industries/zed` commit `4ed72e0135aaab74a43914491c915dd6cbd10c67` (main, 2026-11-09), inspected locally via sparse clone. Line numbers are from that commit. `Z = https://github.com/zed-industries/zed/blob/4ed72e0135aaab74a43914491c915dd6cbd10c67`.

Important structural facts discovered first (they change how to read everything below):

- **Repo layout changed vs. the crates.io release.** The platform backends are no longer in `crates/gpui/src/platform/{mac,windows,linux}`. They are separate crates: `crates/gpui_platform` (facade; `gpui_platform::application()`), `crates/gpui_macos`, `crates/gpui_windows`, `crates/gpui_linux` (x11 + wayland), `crates/gpui_wgpu` (Linux/web renderer), `crates/gpui_web`, `crates/gpui_ios`. The Linux renderer is now **wgpu** (git-pinned rev, not a crates.io release), not blade (`Z/Cargo.toml` L1008-1009; `Z/crates/gpui_linux/Cargo.toml` features `wayland`/`x11` → `gpui_wgpu`).
- **crates.io `gpui` is stale.** Latest published `gpui` is **0.2.2, published 2025-10-22** (crates.io API), Apache-2.0, no MSRV declared. The repo's `crates/gpui/Cargo.toml` still says `version = "0.2.2"`, and `gpui_platform`, `gpui_macos`, `gpui_windows`, `gpui_linux` are **not on crates.io at all** (workspace `publish = false`, `Z/Cargo.toml` L279; crates.io API returns nothing for `gpui_platform`). Issue [#66275](https://github.com/zed-industries/zed/issues/66275) (Oct 2026) asked for a release; a Zed maintainer replied they are "working on automated releases … you will need to pin a git revision" and closed it. So today the real options are (a) git dependency on zed, (b) third-party snapshot crates `gpui-pre` / `gpui-pre-platform` (0.3.12, weekly, published by Longbridge's huacnlee, "snapshot of zed@d2a4fb6"), (c) community fork `gpui-ce` (0.3.0).
- Toolchain: workspace is pinned to Rust **1.98.1**, edition 2024 (`Z/rust-toolchain.toml`). README: "You'll also need to use the latest version of stable Rust" and "There will often be breaking changes between versions" (`Z/crates/gpui/README.md`).

## Details per feature

### 1. Frameless window, custom drag region, resizable edges, min size

- `WindowOptions` (`Z/crates/gpui/src/platform.rs` L2602-2687) has `titlebar: Option<TitlebarOptions>`, `is_movable`, `app_owns_titlebar_drag` (macOS), `is_resizable`, `is_minimizable`, `window_min_size: Option<Size<Pixels>>`, `window_decorations: Option<WindowDecorations>` (`Server|Client`, X11/Wayland), `window_background`, `kind`, `focus`, `show`, `display_id`, `app_id`, `icon` (X11 only), `tabbing_identifier`, `use_display_p3`.
- **Windows** (`Z/crates/gpui_windows/src/window.rs` L480-512): `titlebar: None` ⇒ `hide_title_bar = true`; style `WS_SYSMENU | WS_THICKFRAME | WS_MAXIMIZEBOX` when resizable. `WM_NCCALCSIZE` is handled to remove the frame and `WM_NCHITTEST` (`events.rs` L965-1030) computes resize edges manually (`HTTOPLEFT/HTTOP/...`) when `is_resizable`, and maps `WindowControlArea::Drag` → `HTCAPTION` when `is_movable`. Min size via `WM_GETMINMAXINFO` (`events.rs` L100). Drag region in your UI: `div().window_control_area(WindowControlArea::Drag)` (`Z/crates/gpui/src/elements/div.rs` L1304). Note: `WindowKind::PopUp` uses `WINDOW_STYLE(0)` (no `WS_THICKFRAME`), so a topmost PopUp window's OS-resize behaviour is **unknown** (hit-test still returns HT edges, but whether `DefWindowProc` sizes a non-THICKFRAME window was not verified).
- **macOS** (`Z/crates/gpui_macos/src/window.rs` L1018-1034, L1185-1205): `titlebar: None` ⇒ `Titled | FullSizeContentView` + `setTitlebarAppearsTransparent:YES` + `setTitleVisibility:Hidden` (not `Borderless`), `setContentMinSize`, `setMovable:`; drag via `performWindowDragWithEvent` in `start_window_move` (L2259-2270); `app_owns_titlebar_drag` doc in `platform.rs` L2625-2636.
- **X11** (`Z/crates/gpui_linux/src/linux/x11/window.rs`): client-side decorations through `_MOTIF_WM_HINTS` (L1918-1950, falls back to server decorations when no compositor); `start_window_move`/`start_window_resize` send `_NET_WM_MOVERESIZE` (L1832-1840); min size via `WM_NORMAL_HINTS` (L788-792).
- **Wayland** (`wayland/window.rs`): `xdg_toplevel._move` (L2098-2104), `set_min_size` (L286-287), `zxdg_toplevel_decoration_v1` for CSD/SSD.
- Reference implementation: `Z/crates/gpui/examples/window_shadow.rs` (CSD with `set_client_inset`, `start_window_resize(edge)`, `start_window_move()`), `examples/window_movable.rs`.
- Verdict: **supported**. Minor caveat: drag must be wired two ways (hit-test area on Win/mac vs. `start_window_move` on Linux; `start_window_move` also works on mac).

### 2. Transparent background / per-pixel alpha

- Enum `WindowBackgroundAppearance { Opaque, Transparent, Blurred, MicaBackdrop, MicaAltBackdrop }` (`platform.rs` L2899-2919). Runtime switch: `Window::set_background_appearance` (`window.rs` L3295).
- **Windows**: windows are created with `WS_EX_NOREDIRECTIONBITMAP` and rendered through a **DirectComposition** swap chain with `DXGI_ALPHA_MODE_PREMULTIPLIED` (`gpui_windows/src/window.rs` L513-516; `directx_renderer.rs` L160-181, L1318). `Transparent` additionally calls the undocumented `SetWindowCompositionAttribute` (accent state 2), `Blurred` = acrylic (state 4), Mica via `DWMWA_SYSTEMBACKDROP_TYPE` on build ≥ 22621 (`window.rs` L918-942, L1606-1675). Opt-out env `GPUI_DISABLE_DIRECT_COMPOSITION` falls back to an HWND swapchain with `DXGI_ALPHA_MODE_IGNORE` (no alpha). Open issue #65743 "inappropriate RGBA alpha handling" concerns `Rgba::blend`, not window alpha.
- **macOS**: `setOpaque:NO`, near-clear background colour (alpha 0.0001 "to avoid broken shadow"), Metal layer transparency; `Blurred` inserts an `NSVisualEffectView` subview (`gpui_macos/src/window.rs` L1885-1925).
- **X11**: picks a 32-bit "transparent" visual if available, else warns `Unable to find a transparent visual` and inherits (`x11/window.rs` L487-495); actual blending requires a running compositor. No blur.
- **Wayland**: wgpu surface alpha; blur only through KDE's `org_kde_kwin_blur` (`wayland/window.rs` L32, L112).
- Verdict: **supported on all four**, `Blurred` partial.

### 3. Always-on-top / above a full-screen game

- `WindowKind { Normal, PopUp, AnchoredPopup(PopupOptions), Floating, LayerShell(LayerShellOptions) [linux+wayland], Dialog }` (`platform.rs` L2839-2866). Doc on `PopUp`: "A window that appears above all other windows … use sparingly!".
- **Windows**: `PopUp` ⇒ `WS_EX_TOOLWINDOW | WS_EX_TOPMOST`, style 0 (`gpui_windows/src/window.rs` L494-496). `Floating` has no special handling on Windows (falls into the normal branch). Real-world evidence that PopUp is topmost across apps: issue #51043 / PR #53200 (Copilot sign-in popup "stays on top of all windows"). Electron's `'screen-saver'` level on Windows is also just `HWND_TOPMOST`, so parity is reasonable; neither beats true exclusive-fullscreen DX surfaces (general Windows behaviour, not GPUI-specific — [unverified] here).
- **macOS**: `PopUp` ⇒ `NSPanel` subclass with `NonactivatingPanel` style, `setLevel: NSPopUpWindowLevel (101)`, `CanJoinAllSpaces | FullScreenAuxiliary` (visible over other apps' fullscreen spaces) (`gpui_macos/src/window.rs` L1043-1045, L1255-1264). `Floating` ⇒ `NSFloatingWindowLevel (3)`. No API to pick an arbitrary level (e.g. `kCGScreenSaverWindowLevel` 1000) — would need raw handle.
- **X11**: `PopUp` ⇒ `override_redirect = true` + `_NET_WM_WINDOW_TYPE_NOTIFICATION` (`x11/window.rs` L514, L616-626). Override-redirect windows are unmanaged (always above managed windows, no taskbar, but can't be focused via WM, don't move with workspaces semantics, and some compositors treat them oddly). `_NET_WM_STATE_ABOVE` is **not** set anywhere (grep over `gpui_linux/src/linux/x11/*.rs`). `Floating` ⇒ `WM_TRANSIENT_FOR` only (PR #39702: "floating windows on x11 and wayland").
- **Wayland**: `PopUp` has no special code path (plain `xdg_toplevel`); only `WindowKind::LayerShell(LayerShellOptions { layer: Layer::Overlay, anchor, exclusive_zone, margin, keyboard_interactivity })` gives an overlay (`gpui/src/platform/layer_shell.rs`; errors with `LayerShellNotSupportedError` when the compositor lacks `zwlr_layer_shell_v1` — i.e. GNOME). Example: `gpui/examples/layer_shell.rs`.
- Verdict: **partial** — Windows/macOS fine; X11 via unmanaged override-redirect; Wayland only on wlroots/KDE-class compositors.

### 4. Click-through / mouse passthrough

- `Window::set_input_region(&self, region: Option<&[Bounds<Pixels>]>)` — doc: "Linux (wayland) only … `Some(&[])` is an empty region, so the window receives no pointer or touch input. `None` resets" (`window.rs` L2726-2735). Implemented only in `wayland/window.rs` L2147-2175 (`wl_surface.set_input_region` + commit). Default trait impl is a no-op (`platform.rs` L1389).
- No other hit-test passthrough API exists; grep for "click-through/ignore mouse" issues in zed returned 0 results.
- **Escape hatch**: `impl raw_window_handle::HasWindowHandle for Window` and `HasDisplayHandle` (`window.rs` L45, L7868-7880), and `trait PlatformWindow: HasWindowHandle + HasDisplayHandle` (`platform.rs` L1246); Windows additionally has `fn get_raw_handle(&self) -> HWND` (L1370). `raw-window-handle = "0.6"` (`Z/Cargo.toml` L867). With that you can: Windows `SetWindowLongPtrW(hwnd, GWL_EXSTYLE, … | WS_EX_TRANSPARENT | WS_EX_LAYERED)` (toggle at runtime; note GPUI already uses `WS_EX_NOREDIRECTIONBITMAP`, combining with `WS_EX_LAYERED` should be tested — **unknown**); macOS `[NSWindow setIgnoresMouseEvents:]` on the `NSView`'s window; X11 `xfixes_set_window_shape_region(ShapeKind::INPUT, empty)` on the raw window id.
- Verdict: **Wayland supported; others unsupported in-API but feasible via raw handle (unsafe FFI you own).**

### 5. Skip taskbar / dock, all workspaces

- Windows: `WS_EX_TOOLWINDOW` is set only for `WindowKind::PopUp` (`gpui_windows/src/window.rs` L495); Normal windows get `WS_EX_APPWINDOW`. No separate option.
- macOS: `PopUp` sets `CanJoinAllSpaces` (L1263). Dock icon: `App::set_activation_policy(ActivationPolicy::Accessory)` (`app.rs` L2108; `platform.rs` L166-172; `gpui_macos/src/platform.rs` L652).
- X11: no `_NET_WM_STATE_SKIP_TASKBAR` / `_NET_WM_DESKTOP = 0xFFFFFFFF` support; override-redirect PopUp sidesteps the taskbar. Wayland: compositor policy only (LayerShell surfaces are not in task switchers by design).
- Verdict: **partial** (comes bundled with `PopUp`, no fine-grained control).

### 6. Window control & display queries

- Available on `Window`: `activate_window()` (L6919; Wayland uses `xdg_activation` tokens and may only mark "demands attention"), `request_attention()`, `minimize_window()`, `zoom_window()`, `toggle_fullscreen()`, `bounds()` (L3082), `window_bounds()`, `inner_window_bounds()`, `resize(Size)` (L3123), `is_window_active()`, `visibility() -> WindowVisibility {Visible, Hidden}`, `display(cx)`, `set_window_title`, `set_app_id`.
- `App`: `displays()`, `primary_display()`, `find_display(id)`, `windows()`, `active_window()`, `open_window(...)`, `activate(ignoring_other_apps)`, `hide()` (whole app; no-op on Windows, `gpui_windows/src/platform.rs` L696).
- `PlatformDisplay`: `id()`, `uuid()`, `bounds()`, `visible_bounds()` ("excluding taskbar/dock areas", overridden on Windows and macOS; Linux default = full bounds), `refresh_interval()`, `default_bounds()` (`platform.rs` L637-672).
- **Gaps**: no `Window::set_position/set_bounds` and no per-window `hide()/show()` after creation (`PlatformWindow` trait L1246-1460 has none; only `WindowOptions.show` at creation and `map_window()` on Linux). Initial placement via `WindowOptions.window_bounds = Some(WindowBounds::Windowed(bounds))` works (see `examples/window_positioning.rs`). For an overlay that must snap next to the game you'd move via raw handle or close+reopen the window.
- Verdict: **partial**.

### 7. Global hotkeys

- GPUI: nothing (no `RegisterHotKey`, `XGrabKey`, `CGEventTap` in `gpui*/src`). GPUI key bindings only fire when a GPUI window has focus.
- `global-hotkey` 0.10.0 (Apache/MIT, MSRV 1.77, tauri-apps): README "Platforms-supported: Windows, macOS, Linux (X11 Only)". Windows backend creates its own hidden HWND and uses `RegisterHotKey`/`WM_HOTKEY` (src/platform_impl/windows/mod.rs) and requires "a win32 event loop must be running on the thread" — GPUI's main loop is `GetMessageW → TranslateMessage → DispatchMessageW` (`gpui_windows/src/platform.rs` L583-586), which dispatches to any window on the thread, so create the manager inside `Application::run`'s callback (main thread). macOS backend uses Carbon `RegisterEventHotKey` + `InstallEventHandler(GetApplicationEventTarget())`, requires main-thread run loop — satisfied by GPUI's `NSApplication` run. X11 backend spawns its own thread with its own x11rb connection (`std::thread::spawn` + `grab_key`), independent of GPUI. Events arrive on a crossbeam channel (`GlobalHotKeyEvent::receiver()`); poll it from a GPUI background task / timer. No documented conflicts found; none verified empirically here (**unknown** in practice).
- Wayland: unsupported by the crate (issue #28, PR #162 open); the only portable route is the XDG GlobalShortcuts portal (not provided by global-hotkey today).

## API stability, docs, third-party apps

- **Stability**: README: "still pre-1.0. There will often be breaking changes between versions." Observed churn just in the last ~12 months: platform crates split out (`gpui_platform::application()` replaces `Application::new()`), blade → wgpu on Linux, new `WindowKind` variants (`AnchoredPopup`, `LayerShell`, `Floating`, `Dialog`), `PinchEvent`/`ScrollEvent` input changes (#66275). The gpui.rs hello-world still shows `Application::new()`, which no longer matches main's `gpui_platform::application()`. Pin a git rev (or a `gpui-pre` snapshot) and budget for upgrades.
- **Docs**: gpui.rs links to README, crate rustdoc, examples, "Contexts" and "Key Dispatch" pages; the README itself says "the best way to learn about these APIs is to read the Zed source code or drop a question in the Zed Discord". docs.rs/gpui builds but reflects 0.2.2 (2025-10). The `crates/gpui/examples/` directory (≈50 examples incl. `window_shadow`, `window_positioning`, `window_movable`, `layer_shell`, `input`, `drag_drop`, `animation`, `gif_viewer`, `opacity`, `gradient`, `testing`, `toggle_headless`) is the most reliable documentation.
- **Third-party GPUI apps**: Longbridge Pro (commercial trading desktop, mac/Win/Linux, source of gpui-component — gpui-kit README); `your-moon/tern` SSH terminal (macOS primary, "Windows and Linux builds … pass CI but haven't been run on a real desktop yet"); `khromov/gpuix-svelte` (439★, "native desktop apps for Mac, Windows and Linux with Svelte and GPUI", active 2026-11); `MatthiasGrandl/Loungy` (macOS launcher, 1.7k★, archived 2025-10); `hellno/deck` starter (mac+Linux). Evidence for Windows beyond Zed/Longbridge is thin.

## Top risks for an overlay app (Echosight-type)

1. **No supported release channel.** Official crates.io `gpui` is a year stale and lacks the platform crates; main is git-only (wgpu git dep). You either track zed main by rev or trust Longbridge's `gpui-pre` snapshots. Breaking changes are frequent and undocumented outside PR titles.
2. **Click-through is Wayland-only in-API.** On Windows/macOS/X11 you must own `unsafe` FFI through `raw-window-handle` (`WS_EX_TRANSPARENT|WS_EX_LAYERED`, `ignoresMouseEvents`, XFixes). Interaction of `WS_EX_LAYERED` with GPUI's `WS_EX_NOREDIRECTIONBITMAP`/DirectComposition path is unverified.
3. **No runtime window move / per-window hide.** `Window` has `resize()` but no `set_position()`/`hide()`; toggling the overlay means close/reopen or raw-handle calls; on Wayland positioning is impossible by protocol.
4. **Always-on-top is coupled to `WindowKind::PopUp`**, which also implies tool-window/no-taskbar (Win), non-activating panel (mac), override-redirect/unmanaged (X11, so no WM focus or keyboard focus semantics), nothing on Wayland (needs LayerShell → not on GNOME). No independent "topmost" toggle and no choice of macOS window level.
5. **Global hotkeys**: not in GPUI; `global-hotkey` has no Wayland support, and integration with GPUI's loop is plausible-by-design but not verified by any example in either repo.
6. **Windows transparency depends on undocumented `SetWindowCompositionAttribute`** (Win10 1809+) and DirectComposition; `GPUI_DISABLE_DIRECT_COMPOSITION` removes alpha entirely. Exclusive-fullscreen games will still cover any topmost HWND (same as Electron).
7. **Linux fragmentation**: X11 needs a compositor for alpha; Wayland needs wlr-layer-shell for overlay semantics; native prompts don't exist (fallback renderer); `visible_bounds()` (work area) is not implemented on Linux.
8. **No built-in text input**; either hand-write `EntityInputHandler` (as `examples/input.rs`, ~400 lines) or take on gpui-component (and its `gpui-pre` pin).
9. **Build cost / toolchain**: latest stable Rust required (1.98 pinned in repo), MSVC + Windows SDK + CMake on Windows, Vulkan-capable GPU on Linux (software adapters rejected), multi-minute clean builds including wgpu/resvg/taffy.
10. **Binary size, memory and idle GPU usage are unmeasured** here; GPUI redraws at display refresh when dirty and has frame-rate limiting (`inactive_frame_interval`, `low_power_frame_interval`, `thermal_frame_interval` in `WindowOptions`), but no numbers were collected.
